# A2UI Protocol Reference
> **Canonical reference for the "Agent is the App" rendering architecture used by Career Concierge.**
>
> This document is both architectural context for engineers and an instruction contract for AI agents implementing canvas-driven UI. Read it before touching `DonnaChatLane.tsx`, `GeminiLivePanel.tsx`, or any canvas state component.

---

## What A2UI Is

A2UI (Agent-to-UI) is an architectural pattern in which an AI agent drives the frontend interface through **declarative JSON payloads** rather than raw HTML or JavaScript. The agent never writes UI code. Instead, it selects components from a pre-approved catalog and populates them with data. The frontend framework — React + Framer Motion in this project — handles all rendering, animation, and brand application.

This creates a clean contract:
- **Agent decides:** what component appears, what data it contains, and when it transitions
- **Client decides:** how it looks, how it moves, and how it feels

The result is high-fidelity "Framer-like" animation quality combined with agent-driven interface orchestration — neither of which is achievable when the agent produces raw markup.

---

## The Four-Phase Lifecycle

| Phase | Description | In This Codebase |
|---|---|---|
| **1. Generation** | Agent processes user intent and synthesizes a UI component selection + data payload | Gemini Live tool calls (`liveIntakeTools.js`) or Donna's chat response triggers a canvas state transition |
| **2. Transport** | Payload is delivered to the frontend | Tool calls arrive via Gemini Live WebSocket as `FunctionCallPart`; chat-driven transitions use React state; both result in `handleCanvasTransition(state)` |
| **3. Resolution** | Client maps the abstract instruction to a concrete component | `DonnaChatLane.tsx` canvas state machine resolves `CanvasState` → mounted component |
| **4. Rendering** | Framework executes rendering with animation and brand styling | Framer Motion `AnimatePresence` + `A2UICard` spring animation + CSS token system |

The agent never touches phases 3 and 4. This is the guarantee.

## The Closed Component Catalog

**Foundational rule:** Donna/Gemini must only reference components that exist in this catalog. The system instruction must enumerate the catalog explicitly. Any component not in this list is a hallucination — the validate-retry loop catches it.

### Catalog Definition

| Component ID | Type | Canvas State | Purpose |
|---|---|---|---|
| `DonnaReadsYouCard` | Interactive Input | `donna_reads_you` | Single calibration question + inline text input. Captures user's gap statement. |
| `GapRevealCard` | Action Widget | `gap_reveal` | Two-column NOW vs. TARGET gap display + price teaser + proceed/defer CTAs |
| `PackageSelectCards` | Container | `package_selection` | Three offering cards with earned pricing (price last, ghost opacity) |
| `InlineIntakeSection` | Interactive Input | `intake_inline` | IntakeFlow sections rendered as A2UI cards within canvas — no modal |
| `DNAProcessingCard` | Action Widget | `dna_processing` | Scan-line progress signifier — "Mapping Professional DNA" |
| `DNARevealCard` | Container | `dna_reveal` | Condensed brief excerpt + account creation fields (if unauthenticated) |
| `WikiCard` | Action Widget | `landing` (Journey B) | Single wiki section rendered as A2UICard with "Donna, update this" secondary |
| `ArtifactExcerptCard` | Container | `dna_reveal`, `plan_active` | Condensed artifact (brief/plan/dossier) with "Open full view ↗" secondary |
| `InlineAuthCard` | Interactive Input | `pre_purchase_account_creation` | Email + password fields for account creation — appears within canvas, never navigates |
| `VoicePanel` | Interactive Input | `concierge_sync` | Inline voice session mount — GeminiLivePanel or ElevenLabsConvaiPanel |

### What Is NOT in the Catalog

The following must never be generated by the agent as canvas components:
- Raw HTML cards
- Module modal openers (except "Open full view ↗" secondary on ArtifactExcerptCard)
- Pricing tables or comparison grids
- Navigation elements (sidebars, tab bars, breadcrumbs)
- Rounded-corner components of any kind
- Any component not in the table above

## Canvas State Machine

The canvas state is the runtime resolution layer between agent instruction and rendered UI. It lives in `DonnaChatLane.tsx`.

```typescript
// From types.ts — canonical definition
type CanvasState =
  | 'landing'               // Mount state — Journey A chips OR Journey B wiki cards
  | 'donna_reads_you'       // Pre-sale: calibration question card
  | 'gap_reveal'            // Pre-sale: NOW vs TARGET gap card with price teaser
  | 'package_selection'     // Three offering cards with earned pricing
  | 'intake_inline'         // Smart Start intake sections rendered in canvas
  | 'dna_processing'        // Processing signifier
  | 'dna_reveal'            // Brief excerpt card + optional account creation
  | 'plan_active'           // Plan artifact card
  | 'concierge_sync';       // Voice panel inline
```

### Transition Contract

```typescript
const handleCanvasTransition = (next: CanvasState) => {
  // 1. Dissolve current slot content (opacity 0, scale 0.97, 300ms)
  // 2. Wait 300ms
  // 3. Set canvasState to next
  // 4. New component materializes via AnimatePresence (A2UICard spring)
  setTimeout(() => setCanvasState(next), 300);
};
```

**State machine rules:**
- Only one state active at a time
- Transitions always dissolve before materializing
- DonnaState machine (`idle | listening | thinking | speaking`) is independent — never couple canvas transitions to DonnaState
- `landing` is the only state reachable on mount — no other state is set before user interaction

## Response Segmentation

Donna's responses are segmented into two parts that travel together but render differently:

| Part | Official A2A Type | Renders In |
|---|---|---|
| `TextPart` | `{ "type": "text", "text": "..." }` | DonnaChatLane message thread — sentence-by-sentence stagger |
| `DataPart` (canvas instruction) | `FunctionCallPart` via Gemini tool calling | A2UI slot — component materialization |

**Note on MIME types:** The research source referenced `application/json+a2ui` as a MIME type — this is not an official Google or A2A specification. The real mechanism is Gemini's structured output (`responseMimeType: "application/json"` + `responseSchema`) or standard `FunctionCallPart` tool invocations. This project uses tool calls (`liveIntakeTools.js`) as the DataPart layer, which is the correct and production-supported approach.

In practice, segmentation works like this:
1. **Tool calls** — `liveIntakeTools.js` function calls are the DataPart. When Donna calls `onJumpIntakeScreen`, the canvas transitions to `intake_inline`. Donna's spoken confirmation is the TextPart.
2. **Chat-driven transitions** — when Donna's message thread response completes, a `handleCanvasTransition` is scheduled client-side. The message itself is the TextPart; the transition is the DataPart side effect.

The client's `DonnaChatLane` surface controller listens for both and dispatches each to the appropriate renderer.

**A2A reference:** The Google A2A specification (open governance project, not a Google product) defines `Task`, `Message`, `Artifact`, and `AgentCard` as top-level objects. The official spec repo: `https://github.com/google-a2a/A2A`. This project's architecture is philosophically aligned with A2A but does not implement the full protocol — it uses Gemini Live WebSocket as transport and Firebase as the state layer.

## The Generate-Validate-Retry Loop

Because LLMs can occasionally hallucinate incorrect state transitions or non-catalog components, the canvas state machine implements a validation layer:

### Validation Rules

```typescript
const VALID_CANVAS_STATES = new Set<CanvasState>([
  'landing', 'donna_reads_you', 'gap_reveal', 'package_selection',
  'intake_inline', 'dna_processing', 'dna_reveal', 'plan_active', 'concierge_sync'
]);

// Before any transition:
const safeTransition = (next: string): void => {
  if (!VALID_CANVAS_STATES.has(next as CanvasState)) {
    console.warn(`[A2UI] Invalid canvas state requested: "${next}" — ignoring`);
    return; // Graceful degradation: stay at current state
  }
  handleCanvasTransition(next as CanvasState);
};
```

### Sequence Validation

Certain transitions are invalid regardless of agent intent:

```typescript
const INVALID_TRANSITIONS: Partial<Record<CanvasState, CanvasState[]>> = {
  landing: ['dna_processing', 'dna_reveal', 'plan_active'],  // Must go through intake first
  donna_reads_you: ['package_selection'],  // Must go through gap_reveal
  package_selection: ['landing'],  // Can't go backward without explicit reset
};

const isValidTransition = (from: CanvasState, to: CanvasState): boolean => {
  return !INVALID_TRANSITIONS[from]?.includes(to);
};
```

### Graceful Degradation

If a transition is blocked by validation, the system:
1. Keeps the current canvas state
2. Lets Donna's message thread response render normally (TextPart always succeeds)
3. Logs the invalid attempt for debugging
4. Does NOT crash or show an error to the user

This mirrors the A2UI specification: if the DataPart fails validation, fall back to a plain text response. The conversation continues; only the canvas component fails to mount.

## State and Interactive Journeys

UI interactions in the A2UI canvas are not chat messages — they are **tool triggers**. This distinction is critical for the agent context contract.

### Interaction → Tool Call Mapping

| User Action | Canvas Event | Backend Action |
|---|---|---|
| Submits calibration answer | `handleCalibrationSubmit()` → `donna_reads_you` response | Donna LLM call with calibration answer as context |
| Clicks "SHOW ME HOW →" on gap card | `handleCanvasTransition('package_selection')` | No backend call — pure state transition |
| Clicks package card CTA | `handleCanvasTransition('intake_inline')` | `onJumpIntakeScreen` tool sets intake section |
| Intake section complete | `handleCanvasTransition('dna_processing')` | Artifact generation API call fires in background |
| Voice session opens | `handleCanvasTransition('concierge_sync')` | `createGeminiLiveToken` with wiki context |

### Skeleton / Loading States

For transitions that involve backend calls (processing, artifact generation), the canvas renders loading state components:

- `DNAProcessingCard` — rendered during `dna_processing`; shows animated scan-line, not a spinner
- Use `DNAProcessingCard` as the pattern reference for any future loading state — never a circular spinner, always a linear scan or typed progress indicator

## Tool Grammar Integration

The A2UI canvas state machine connects to the existing `liveIntakeTools.js` tool grammar. The following tools have direct canvas state implications:

| Tool Name | Canvas State Triggered |
|---|---|
| `onJumpIntakeScreen` | `intake_inline` |
| `onIntakeComplete` | `dna_processing` → auto-advances to `dna_reveal` |
| `onOpenBrief` | `dna_reveal` |
| `onOpenPlan` | `plan_active` |

**Extending the tool grammar:** When adding new tools that should drive canvas state, add them to `liveIntakeTools.js` following the existing schema — never fork or rename existing tools. The canvas state machine in `DonnaChatLane.tsx` listens for these callbacks via the `intakeCallbacks` prop.

## A2UI Payload Schema (TypeScript)

The formal TypeScript types for the A2UI layer live in `types.ts`. See the `// ─── A2UI` section for:

- `CanvasState` — the full state union
- `A2UIComponentType` — the closed catalog as a union type
- `A2UIPayload` — the JSON envelope
- Per-component data interfaces (`GapRevealData`, `PackageSelectData`, etc.)

These types are the contract between the agent's instruction layer and the React rendering layer. The agent prompt must reference the component IDs from `A2UIComponentType` — nothing else.

## Security and Deployment Notes

The A2UI rendering layer is client-side React — it executes no server code. Security perimeter is maintained at:

1. **API routes** — all agent context routes (`/v1/wiki/context`, `/v1/memory/context`, `/v1/live/token`) require Firebase auth via `requireAuth` middleware
2. **Component isolation** — the closed catalog prevents the agent from triggering arbitrary DOM manipulation or navigation
3. **Tool call schema validation** — `liveIntakeTools.js` schemas are validated by the Gemini Live function calling layer before any callback fires
4. **Canvas state validation** — the `safeTransition` guard (above) prevents invalid states from mounting

For production: the Gemini Live token endpoint (`/v1/live/token`) should be the only surface that receives unvalidated agent output. Everything downstream is schema-gated.

## Source Accuracy Notes

The research provided as input to this document contained several inaccuracies. Corrected below for agent reference:

| Claim in Source | Reality |
|---|---|
| "Gemini 3.1 Flash Live" | **Confirmed correct.** Real model, announced by Google. Described as "our highest-quality audio and voice model yet" — 90.8% on ComplexFuncBench Audio for multi-step function calling, real-time voice, 200+ languages, SynthID watermarking. This IS the right model for Donna's voice layer. Use exclusively for live sessions. |
| `application/json+a2ui` MIME type | Not an officially registered MIME type. The real underlying mechanism is Gemini function calling (`FunctionCallPart`) — which is exactly what `liveIntakeTools.js` uses. The pattern is valid; the MIME label is informal/coined. |
| AG2 as a Google framework | False. AG2 is the community fork of Microsoft's AutoGen — unaffiliated with Google. |
| A2A as a Google product | A2A is an open governance spec initiated by Google but not a Google product. `github.com/google-a2a/A2A` |

The architectural pattern described (declarative JSON, closed catalog, validate-retry, segmented transport) is accurate and well-grounded. The subagent that reviewed this had a training data cutoff before Gemini 3.1 Flash Live was announced — the model is real and current.
